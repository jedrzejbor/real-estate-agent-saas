# PAY-015 — kontrola konfiguracji 13 października 2026 r.

- Zakres: tylko walidacja `PAYMENT_PROVIDER`, adresu API i wymaganych danych backendowych; bez klienta HTTP, tokenu, checkoutu, webhooka i zmian bazy.
- Konfiguracja: istniejące wartości `TPAY_API_URL`, `TPAY_CLIENT_ID`, `TPAY_CLIENT_SECRET` i `TPAY_MERCHANT_ID` pozostały w ignorowanym `apps/api/.env.local`. Ich wartości nie zostały zapisane w protokole. `PAYMENT_PROVIDER=tpay` ustawiono wyłącznie dla procesu testowego. `TPAY_SECURITY_CODE` nie jest wymagany przez PAY-015; będzie potrzebny przy późniejszym webhooku. Domyślny provider w dotychczasowej aplikacji to `disabled`.
- Testy jednostkowe PAY-015: **PASS, 5/5** (`tpay.config.spec.ts`). Nieznany provider i brak sekretu zatrzymują inicjalizację modułu; komunikat błędu i przechwycone logi nie zawierają sekretu. Test potwierdza odrzucenie URL Sandbox w trybie produkcyjnym i poprawny tryb wyłączony.
- Kontrola ręczna startu: **PASS** — API uruchomiono lokalnie z konfiguracją Sandbox i testowym JWT na porcie 4001; `/api` odpowiedziało HTTP 200. Skrypt sprawdził obecność trzech lokalnych wartości uwierzytelniających w logu bez ich wypisywania: **0 znalezionych**. Proces testowy zatrzymano. Pierwsza próba poza Dockerem wymagała testowego `JWT_SECRET`; pierwsza próba połączenia z bazą była ograniczona przez sandbox narzędzia, więc start powtórzono z dostępem do lokalnego PostgreSQL. Nie był to błąd konfiguracji Tpay.
- Migracje i zmiany schematu bazy: **brak**. PAY-015 nie zapisuje danych płatności; nie porównywano wszystkich rekordów aplikacji przed i po starcie. Nie wykonano żądania do Tpay. Checkout pozostał wyłączony.
- Pozostałe ograniczenia: zapytanie PAY-003 do Tpay pozostaje niewysłane; osobny błąd schedulera o brakującej `agency_plan_checkout_attempts` i dodatkowe kontrole ról/flag PAY-011 pozostają odnotowane poza zakresem PAY-015.
