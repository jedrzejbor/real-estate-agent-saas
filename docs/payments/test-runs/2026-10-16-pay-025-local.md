# PAY-025 / MT-006 — weryfikacja podpisu JWS

- Data: 16 października 2026 r.; środowisko: lokalne; publiczny checkout nadal wyłączony.
- Podstawa protokołu: [Tpay Webhooks](https://docs-api.tpay.com/en/webhooks/) opisuje nagłówek `X-JWS-Signature`, odłączony podpis nad dokładnym body, certyfikat podpisujący i Tpay CA. Dokumentacja pokazuje podpis RSA/SHA-256; weryfikator dopuszcza tylko `RS256` oraz dokładny URL dokumentowanego certyfikatu w `x5u`.
- Testy automatyczne: **Pass, 7/7** (`pnpm --filter api test -- --runInBand src/payments/infrastructure/tpay/tpay-jws.verifier.spec.ts`). Sprawdzono poprawny podpis, zły podpis, zmienione bajty body, obcy CA, niedozwolone `x5u`, inny algorytm, brak danych i pobranie wyłącznie dwóch stałych URL z cache. Certyfikaty testowe powstają lokalnie; testy nie łączą się z Tpay.
- MT-006 — ręczne wysłanie błędnego webhooka do aplikacji: **Blocked**. PAY-026 nie dodał jeszcze endpointu Tpay, więc nie ma istniejącej bezpiecznej powierzchni, na której można wysłać fixture i sprawdzić stan płatności w aplikacji. Wynik testu jednostkowego nie jest zaliczeniem tego scenariusza ręcznego.
- Dane i zachowanie: brak migracji, zmian bazy, nowych żądań płatniczych i zmian checkoutu. Nie wysłano żadnej notyfikacji ani zapytania do Tpay. Nie zapisano surowego body, certyfikatów, tokenów ani danych dostępowych w logach lub protokole.
- `docs/MANUAL_RELEASE_TESTS.md`: bez zmian, ponieważ PAY-025 dodaje tylko niepodłączony weryfikator i nie zmienia obecnej ścieżki odbioru manualnego. Istniejący scenariusz PAY-07 obejmuje odrzucenie błędnego podpisu po wdrożeniu endpointu.

Manual regression required: MT-006 po PAY-026. MT-004 i pełny powrót z PAY-023 pozostają osobno zablokowane zgodnie z wcześniejszymi protokołami.
