# PAY-026 / MT-006 — cienki endpoint Tpay webhook

- Data: 16 października 2026 r.; środowisko: lokalny API i lokalna baza Docker. Checkout nadal wyłączony.
- Testy automatyczne: **Pass, 4/4** (`pnpm --filter api test -- --runInBand src/payments/infrastructure/tpay/tpay-webhook.controller.spec.ts`). Sprawdzono `200 TRUE` po pozytywnej odpowiedzi weryfikatora, przekazanie dokładnego raw body, `401` dla błędnego/brakującego JWS, `415` dla innego typu body i brak redirectu. Weryfikator był mockowany; testy nie kontaktowały się z Tpay ani bazą. Pierwszy przebieg w piaskownicy był blokowany przez `listen EPERM`; ten sam zestaw przeszedł po uruchomieniu z dostępem do lokalnego portu.
- MT-006, lokalna próba z błędnym JWS: **Pass w zakresie transportu**. `POST /api/payments/webhooks/tpay` bez sesji, z testowym form body i celowo błędnym podpisem zwrócił HTTP `401`, komunikat `Invalid webhook signature` i brak przekierowania. Początkowo globalny JWT guard zatrzymywał żądanie; dodano `@Public()`, po czym odpowiedź pochodziła z kontrolera. Nie podano danych karty ani sekretów.
- Odczyt bazy przed i po ponowionej błędnej notyfikacji: `listing_orders` 0 → 0 i `listing_entitlements` 0 → 0. W tej lokalnej bazie nie ma tabeli `payments`, więc nie można było porównać statusu oczekującej lokalnej płatności. Nie wykonywano migracji ani zapisów.
- Pełne MT-006: **Blocked**. Brak oczekującego lokalnego `Payment` do porównania i nie udało się niezależnie odczytać wpisu odrzucenia w logach kontenera. Logowanie kontrolera zawiera jedynie stały komunikat bez body; test kontrolera potwierdza brak surowej notyfikacji w wywołaniu loggera.
- Poprawnie podpisany webhook otrzymuje `TRUE`, ale PAY-026 nie utrwala go i nie rozlicza płatności. **Nie konfiguruj tego adresu dla produkcyjnych powiadomień** przed wdrożeniem trwałego ledgeru i obsługi zdarzeń. Nie wykonano żądań płatniczych do Tpay, zmian schematu ani zmian uprawnień.

Manual regression required: MT-006 po przygotowaniu trwałego przetwarzania i lokalnej oczekującej płatności.
