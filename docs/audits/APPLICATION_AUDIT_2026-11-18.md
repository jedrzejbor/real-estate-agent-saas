**Decyzja wydaniowa: wstrzymać publiczny start, również w wariancie bez płatności.** Skompilowane API zatrzymuje się podczas tworzenia usługi zwrotów. Po usunięciu tego błędu udostępnienie obecnego kodu otworzyłoby CRM z wadliwą izolacją relacji spotkań, publiczne strony z niebezpiecznym osadzaniem treści i sesje, których właściciel konta nie może skutecznie odwołać. ## Ustalenia według ryzyka

### PA-01 · API zatrzymuje się podczas inicjalizacji usługi zwrotów

**High · niezawodność · potwierdzony wykonaniem · pewność wysoka · blokuje każdy start API.** API `listing-commerce/listing-refunds.service.ts:14–18`, `listing-commerce/listing-commerce.module.ts:108`, `payments/payments.module.ts:60–75`. Moduł eksportuje provider pod tokenem klasy adaptera. Kompilator emituje dla parametru `TpayPaymentAdapter | null` token DI `Object`. Nest próbuje rozwiązać inny token niż zarejestrowany. Dotyczy samego uruchomienia, bez zalogowanego użytkownika, także przy wyłączonych płatnościach.

**Dowód.** Odczyt metadanych ze świeżego builda zwrócił `[DataSource, PaymentService, Object]`. Kompilacja pełnego `AppModule` z podstawionym DataSource i wyłączonym providerem płatności zakończyła się komunikatem Nest o brakującej zależności nr 2 w `ListingRefundsService`. Test używa rzeczywistej rejestracji usług, bez HTTP, bazy i operatora. **Naprawa i odbiór:** jawny token DI dla opcjonalnej wartości adaptera. Skompilować pełny moduł dla obu konfiguracji operatora, uruchomić binarium na izolowanym stagingu i sprawdzić gotowość do obsługi danych.

### PA-02 · Spotkanie może zwrócić klienta lub ofertę innego agenta

**High · kontrola dostępu · potwierdzony w kodzie · pewność wysoka · blokuje CRM.** API `appointments/appointments.controller.ts:27–34`, `appointments/dto/create-appointment.dto.ts:39–46`, `appointments/appointments.service.ts:50–74,92–96,147–175,273–291`, `appointments/entities/appointment.entity.ts:64–77`. SQL `20260623_appointment_relation_columns.sql:27–32`. DTO sprawdza format identyfikatorów. Serwis przypisuje właściciela spotkania z sesji, ale przy tworzeniu przyjmuje też powiązania z DTO. Odczyt po zapisie i lista ładują pełne relacje. FK weryfikuje istnienie obiektu. Żadne z tych sprawdzeń nie porównuje właściciela klienta/oferty z agentem spotkania.

**Warunek i skutek.** Konto z możliwością utworzenia spotkania i znanym identyfikatorem istniejącego powiązanego rekordu. W odpowiedzi mogą znaleźć się dane kontaktowe, budżet i notatki klienta lub wewnętrzne pola oferty. Zakres pól wynika z API `clients/entities/client.entity.ts:23–50`. Kontrola własności samego spotkania przy edycji nie wystarcza. Dowodem jest ścieżka zapisu i zwrotu encji oraz definicja FK. **Naprawa i odbiór:** rozwiązywać każdą relację w zakresie agenta przy create i patch, osłonić odczyt istniejących błędnych relacji, przejrzeć je przed migracją. Wzorzec istnieje w `tasks/tasks.service.ts:248–252,326–335`. Test regresji na dwóch syntetycznych agencjach powinien potwierdzić odmowę bez zapisu, brak cudzych pól na liście oraz poprawne działanie własnych relacji.

### PA-03 · Treść opublikowanej oferty trafia bez kodowania HTML do JSON-LD

**High · stored XSS · potwierdzona niebezpieczna serializacja · pewność wysoka · blokuje publiczny katalog.** API `listings/dto/create-listing.dto.ts:64–74`, `listings/listings.service.ts:1266–1282,1897–1898`; WEB `app/(public)/oferty/[slug]/page.tsx:132–142,561–562`, `app/(public)/agenci/[id]/page.tsx:111,350`, `app/(marketing)/blog/[slug]/page.tsx:135–144`. Tytuł i opis oferty przechodzą do obiektu danych strukturalnych, potem do surowej zawartości elementu script. Serializacja do JSON pozostawia znaki znaczące dla parsera HTML. Moderacja biznesowa ocenia m.in. ryzyko spamu i cenę. Nie koduje tekstu dla tego kontekstu. Blog ma węższy krąg autorów.

**Warunek i skutek.** Wpływ na publikowaną treść i odwiedziny strony. Możliwe wykonanie skryptu w originie serwisu, także podczas sesji użytkownika. HttpOnly ogranicza bezpośredni odczyt cookies. Faktyczna polityka CSP na hostingu pozostaje nieznana. **Naprawa i odbiór:** jeden serializer JSON-LD z kodowaniem znaków HTML, użyty we wszystkich pięciu miejscach, oraz CSP dobrana do skryptów aplikacji. Test wyrenderowanego HTML z obojętnym tekstem zawierającym znaczniki musi zachować pojedynczy element JSON-LD, odtworzyć tekst po parsowaniu JSON i nie utworzyć dodatkowych węzłów.

### PA-04 · Zmiana hasła i wylogowanie nie odwołują wydanych sesji

**High · bezpieczeństwo kont · potwierdzony w kodzie · pewność wysoka · blokuje publiczne konta.** API `auth/auth.service.ts:184–190,215–232,259–280,314–326`, `auth/auth.controller.ts:116–135`, `auth/strategies/jwt.strategy.ts:17–41`, `auth/strategies/jwt-refresh.strategy.ts:23–43`, `users/users.service.ts:333–343,361–379`. Oba JWT mają ten sam klucz, te same pola i różne czasy ważności. Strategie walidują podpis, datę i użytkownika w DB. Żadna nie wymaga odrębnego przeznaczenia tokena ani aktywnego rekordu sesji. Wydanie następnej pary nie zużywa poprzedniej. Logout kasuje cookies, reset i zmiana hasła aktualizują hash.

**Warunek i skutek.** Uprzednie uzyskanie ważnego tokena aktywnego konta. Okno dostępu może przeżyć logout lub zmianę hasła, a ponowne odświeżanie wydłuża ten dostęp. Domyślne TTL to 15 minut i 7 dni. Blokada konta jest sprawdzana przy obu ścieżkach, a rola i uprawnienia dla żądań są pobierane z DB. Osobno, reset weryfikuje hash i czas, po czym zapisuje po samym ID. Dwie równoległe realizacje poprawnego tokena mogą przejść etap weryfikacji przed jego zużyciem.

**Naprawa i odbiór:** rozdzielić przeznaczenie JWT, powiązać refresh z sesją w DB, atomowo rotować i wykrywać ponowne użycie. Odwoływać odpowiednie sesje przy logout i wszystkie przy resecie/zmianie hasła. Zużywać token resetu warunkowym UPDATE z datą wygaśnięcia. Sprawdzić poprzednią parę po każdej operacji oraz dokładnie jeden sukces przy równoległym potwierdzeniu resetu.

### PA-05 · Lokalny build obrazu obejmuje konfigurację API i katalog danych

**High · bezpieczeństwo dostaw · reguły kopiowania potwierdzone, zawartość opublikowanych obrazów nieznana · pewność wysoka · blokuje dystrybucję obecnego obrazu z drzewa deweloperskiego.** `.dockerignore:1–6`, `Dockerfile.api:19–25`, API `app.module.ts:50–55`. Dockerfile kopiuje cały katalog aplikacji. W badanym workspace istnieją `apps/api/.env.local` (lokalna konfiguracja, wartość **[zamaskowano]**) i katalog uploadów. Lista wykluczeń Docker nie obejmuje żadnego z nich. Nest czyta ten sam plik przy starcie. Stan śledzenia w Git nie ogranicza kontekstu lokalnego builda.

**Warunek i skutek.** Osoba buduje obraz z takim katalogiem i udostępnia warstwy, cache albo obraz. Potencjalnie dystrybuuje ustawienia, dane uwierzytelniające lub pliki klientów obecne podczas budowy. Potwierdzono obecność pliku po nazwie i działanie reguły COPY, bez odczytu wartości i bez budowania obrazu z danymi użytkownika. Czysty checkout w CI ma inny kontekst. **Naprawa i odbiór:** ograniczyć COPY do artefaktów runtime i wykluczyć konfiguracje lokalne, dokumenty i uploady z kontekstu. Sprawdzić wszystkie warstwy obrazu z syntetycznymi plikami znacznikowymi. Jeżeli obrazy deweloperskie zostały udostępnione, ustalić ich pochodzenie i zakres potrzebnej rotacji.

### PA-06 · Dostarczony mechanizm migracji może zakończyć się częściowym schematem

**High · dane i wdrożenie · potwierdzony w skryptach · pewność wysoka · blokuje wdrożenie i odtwarzanie oparte na tej procedurze.** `package.json:7`, SQL `20260429_freemium_public_listings_and_analytics.sql:21`, `20261011_recurring_authorizations.sql:4–6`, `20261011_subscriptions.sql:4`, `20261020_refund_actor.sql:4`, `20261020_refunds.sql:4`, `.github/workflows/deploy.yml:111–117`. Pierwsza migracja oczekuje istniejącej tabeli listings. W porządku nazw wykorzystywanym przez pętlę pliki z FK do subscriptions poprzedzają utworzenie subscriptions. Zmiana refunds poprzedza utworzenie refunds. Repozytorium nie zawiera pełnego baseline tworzącego bazowe tabele użytkowników, ofert i agencji.

**Dowód i skutek.** Zależności wynikają z ALTER/REFERENCES oraz kolejności nazw. ON_ERROR_STOP zatrzymuje pojedynczy proces psql. Pętla powłoki nie przerywa po jego błędzie, więc późniejszy sukces może przesłonić wcześniejszą porażkę. Warunkiem jest brak wymaganej tabeli lub inny błąd migracji. Część DDL może zostać zatwierdzona, a aplikacja napotyka błędy dopiero przy użyciu funkcji. Synchronizacja TypeORM jest domyślnie wyłączona. **Naprawa i odbiór:** wersjonowany baseline i rejestr wykonania, jawna kolejność zależności, natychmiastowe zatrzymanie pipeline i kontrola wersji schematu przed przełączeniem ruchu. Sprawdzić osobno pustą bazę i zanonimizowaną kopię poprzedniej wersji, komplet FK/indeksów oraz zachowanie danych. Uwzględnić historyczną migrację usuwającą kolumny, bez automatycznego powtarzania operacji na roboczej bazie.

### PA-07 · Poprawna notyfikacja Tpay bez pola waluty nie może zakończyć realizacji

**High dla płatnego wydania · błąd kontraktu · potwierdzony w kodzie i specyfikacji · pewność wysoka · blokuje sprzedaż ogłoszeń.** API `payments/infrastructure/tpay/tpay-webhook.controller.ts:75–82,128–143`, `payments/application/payment.service.ts:245–263`. Parser reprezentuje brak tr_currency jako null. Realizacja wymaga równości z niepustą walutą lokalnej płatności. Dokumentacja Tpay odróżnia pola zawsze obecne od opcjonalnych i nie oznacza tr_currency jako zawsze obecnego. [Parametry notyfikacji Tpay](https://docs-api.tpay.com/pl/webhooks/)

**Warunek i skutek.** Autentyczne podpisane potwierdzenie dokładnej wpłaty bez opcjonalnego pola. Porównanie null z PLN kończy się konfliktem i rollbackiem transakcji obejmującej ledger. Kolejne identyczne powiadomienie ma ten sam wynik. Klient mógłby zapłacić i nie dostać publikacji. Żadne konto klienta nie może samodzielnie nadać podpisu. Częstość tego wariantu dla konkretnego merchanta nie została zmierzona. **Naprawa i odbiór:** przy braku pola uzgodnić walutę przez autoryzowany odczyt transakcji u operatora i sprawdzić wszystkie identyfikatory oraz kwoty, zachowując stan oczekujący do uzgodnienia. Testy dla brakującej, niezgodnej i zgodnej waluty, niedostępnego odczytu i ponowienia mają wykazać dokładnie jedno uprawnienie po potwierdzeniu.

### PA-08 · Pełny zwrot może otrzymać ACK bez aktualizacji płatności i uprawnień

**High dla płatnego wydania · spójność finansowa · potwierdzony w kodzie · pewność wysoka · blokuje obsługę rzeczywistych wpłat i zwrotów.** API `payments/infrastructure/tpay/tpay-webhook.controller.ts:72–96,124–143`, `payments/application/payment.service.ts:110–159,194–231,249–271`, `listing-commerce/listing-refunds.service.ts:20–48`. Tpay definiuje chargeback w tej notyfikacji jako pełny zwrot, także wykonany w panelu akceptanta. Parser oznacza go jako refunded. Kontroler utrwala zdarzenie i odpowiada TRUE. Tylko gałąź confirmed wykonuje weryfikację lokalnego odbiorcy/zamówienia i realizację. Dla zwrotu możliwy jest wpis nawet bez dopasowanej płatności. [Znaczenie tr_status w Tpay](https://docs-api.tpay.com/pl/webhooks/)

**Warunek i skutek.** Podpisane zdarzenie operatora dotyczące wcześniejszej wpłaty. Payment i zamówienie mogą nadal wyglądać na opłacone, a przyznane uprawnienie pozostać aktywne. W lokalnym procesie zwrotu rezerwacja kwoty, unikalny klucz intencji i blokada płatności ograniczają zdublowanie zlecenia. Metoda reconcileRefund sprawdza kwotę i walutę oraz zapisuje rekord Refund. W kodzie wykonawczym nie znaleziono jej wywołania przez scheduler. Restart po rezerwacji może pozostawić status requesting oczekujący na uzgodnienie. **Naprawa i odbiór:** transakcyjnie powiązać pełny zwrot ze zweryfikowaną płatnością, obsłużyć go również po czasie i przed opóźnionym sukcesem. Ustalić zasady cofnięcia lub pozostawienia częściowo wykorzystanego świadczenia i udokumentować je w historii klienta. Testy zwrotu z panelu, częściowego zwrotu, duplikatu i restartu powinny uzgodnić saldo, stan zamówienia i uprawnienia bez kolejnego POST do operatora.

### PA-09 · Publiczny frontend korzysta z wersji objętych biuletynami bezpieczeństwa

**High jako bramka aktualizacji · zależności · dopasowanie wersji potwierdzone, osiągalność poszczególnych błędów warunkowa · pewność wysoka dla wersji.** `pnpm-lock.yaml:3737,3791,4155,4330`, `apps/web/next.config.ts:3–10`, API `email/email.service.ts:46–58`. Next 16.2.2 mieści się w zakresie 16.0.0–poniżej 16.2.5 dla DoS RSC. W badanym buildzie manifest Server Actions ma zero wpisów node i edge. Nie wykazano załamania serwisu przez tę ścieżkę. Październikowy biuletyn wskazuje też ryzyko natywnego optymalizatora obrazów na Linux/glibc. Lockfile ma sharp 0.34.5, obraz deweloperski używa Alpine, a platforma finalnego hostingu jest niezweryfikowana. Brak włączonego cacheComponents i użycia dyrektywy use cache ogranicza zastosowanie biuletynów dotyczących tych funkcji. [Advisory Next.js](https://github.com/vercel/next.js/security/advisories/GHSA-8h8q-6873-q5fj) · [Biuletyn październikowy](https://nextjs.org/blog/nextjs-security-update-october-14-2026) · [Wydanie listopadowe](https://nextjs.org/blog/november-2026-security-release)

Nodemailer 6.10.1 jest poniżej poprawki parsera adresów z 7.0.11. Do wpływu w aplikacji potrzeba wejścia docierającego do podatnego parsera. Sprawdzone DTO e-mail i budowanie wiadomości z osobnych pól ograniczają takie wejście. Nie przypisano aplikacji skutecznego DoS ani RCE. ### PA-19 · Logowanie ujawnia dezaktywację konta, a limity są lokalne dla procesu

**Low dla ujawnienia statusu · bezpieczeństwo kont · potwierdzony w kodzie · pewność wysoka · samodzielnie nie blokuje startu jednej kontrolowanej instancji.** API `auth/auth.service.ts:146–169`, `auth/auth.controller.ts:47–89`, `app.module.ts:71,106–109`, `main.ts:12–18`. Przy wyłączonej weryfikacji e-mail rejestracja propaguje także błąd duplikatu, przy włączonej zwraca neutralny status. W resecie zwykle zwracany jest neutralny sukces, ale tylko istniejące konto czeka na SMTP, więc błąd dostawy może różnicować odpowiedzi. Niezalogowana osoba może poznać stan części adresów. Nie mierzono rozkładów czasu ani skuteczności zgadywania haseł.

Globalny limit dotyczy też kontrolera notyfikacji Tpay, co należy uwzględnić przy wielu dostawach z jednego IP. **Naprawa i odbiór:** ujednolicić komunikaty i koszt porównań, limitować logowanie per konto i IP we wspólnym magazynie, oddzielnie zaprojektować przepustowość webhooków. Zweryfikować status i treść odpowiedzi dla trzech stanów konta, błędu SMTP oraz konsekwentne zliczanie przez dwie repliki za rzeczywistym proxy.

## Kontrole, które zmieniają interpretację wcześniejszych raportów

- **Rejestracja i weryfikacja adresu.** Historyczny zarzut nadawania enterprise wprost z formularza nie odpowiada aktualnej ścieżce. Serwer wybiera Free, tworzy komplet User/Agency/Agent w transakcji i może zwrócić stan oczekujący bez cookies. Weryfikacja jest dostępna, domyślnie wyłączona. Nowe konta z wymogiem potwierdzenia są sprawdzane przy loginie i obu strategiach. Stare konta bez daty wymagania mają inną politykę, a wybrane działania wrażliwe mają dodatkową kontrolę. Potwierdzenie adresu używa warunkowej aktualizacji po hashu i terminie, rezerwacja wysyłki używa transakcji, cooldownu i limitu. Token jest we fragmencie URL, frontend go usuwa. Reset hasła nadal używa query stringu. Sprawdzić redakcję pełnych URL w telemetryce proxy. API `auth/auth.service.ts:62–141,329–338`, `auth/account-email-verification.service.ts:96–119,132–191,249–265`, `auth/account-email-access.policy.ts:8–28`, WEB `app/(auth)/verify-email/verify-email-client.tsx:31`.
- **Cookies, CSRF, subdomeny.** Cookies autoryzacyjne mają HttpOnly, path=/ i Secure w produkcji, domyślnie SameSite=Lax i brak Domain. Przy zapisie z cookies guard wymaga zgodności czytelnego cookie z nagłówkiem. Dla oddzielnego hosta API frontend może pobrać wartość z credentialed GET. CORS ogranicza origin do FRONTEND_URL. Jednoczesne odświeżanie czytelnego cookie z kilku kart może skutkować chwilowym 403, co wymaga odbioru w docelowej topologii. Express ufa wyłącznie skonfigurowanym CIDR proxy, a fingerprint bierze IP z Express. Historyczny zarzut bezwarunkowego zaufania do nagłówka nie znajduje potwierdzenia w tym miejscu. API `auth/auth-token-cookies.ts:20–64,111–132`, `auth/guards/csrf.guard.ts:19–50`, `common/abuse-protection.ts:166`, WEB `lib/csrf.ts:23–64`.
- **Izolacja poza spotkaniami.** Przykładowa transakcja najpierw rozwiązuje ofertę oraz obu klientów w zakresie agenta, potem zapisuje transakcję, zadania i zdarzenie wspólnie. Search w trzech gałęziach wiąże parametry, filtruje po agentId i ogranicza wyniki. Raporty sprawdzają zakres wybranego agenta, a raport bloga jawnie agreguje dane całego serwisu i ignoruje kontekst konta. Docelowy odbiorca tego ostatniego raportu wymaga decyzji właściciela produktu. Dla dokumentów powiązanie listingId/documentId/agentId jest sprawdzane przed odczytem streamu. Publiczne zdjęcia są dostępne bezpośrednio po URL niezależnie od uprawnień dokumentów. Wycofanie oferty nie jest kontrolą dostępu do pliku zdjęcia. API `transactions/transactions.service.ts:94–106,148–168`, `search/search.service.ts:63–65,91–107,130–144,167–188`, `reports/reports.service.ts:748–774,949–1010`, `listing-documents/listing-documents.service.ts:331–360,485–495`.
- **Walidacja, SQL i frontend.** Globalny ValidationPipe odrzuca nieznane pola dla klas DTO. Przykład spotkań pokazuje wagę kontroli dozwolonych relacji także po walidacji. Sortowanie spotkań używa listy kolumn, search używa bindowanych parametrów, a rozdzielczość czasu raportów pochodzi z zamkniętego switcha. W tej próbce nie potwierdzono SQL injection. Geokoder używa stałego hosta, a dane adresowe umieszcza w URLSearchParams. Ścieżka pobrania dokumentu sprawdza przynależność do prywatnego katalogu. W kodzie web znalezione bezpośrednie odwołania NEXT_PUBLIC dotyczą URL API/serwisu, konfiguracji mapy i środowiska checkoutu. Szukanie typowych sygnatur kluczy w kodzie źródłowym i workflow nie dało trafień. Nie badano prywatnych konfiguracji ani wszystkich artefaktów hostingu. API `main.ts:27–32`, `appointments/appointments.service.ts:100–103`, `reports/reports.service.ts:2511–2518`, `locations/google-geocoding.provider.ts:38–54`, `listing-documents/listing-documents.service.ts:560–565`.
- **Cache, nagłówki i eksport.** Publiczna strona pobiera dane po slugu przez publiczne API. Sprawdzony klient panelu używa cookies przeglądarki. W przeszukanych źródłach web nie znaleziono wspólnego cache danych prywatnego użytkownika przez use cache lub unstable_cache. Nie sprawdzono izolacji nagłówków Cache-Control/Vary na CDN. Repo ustawia Referrer-Policy dla weryfikacji e-maila. Nie znaleziono ogólnej CSP lub HSTS aplikacji, mogą pochodzić z proxy. Import CSV klientów podlega DTO z limitem 100 wierszy. Potwierdzono odczyty raportowe, nie wykazano pełnego eksportu konta, anonimizacji ani technicznego usunięcia wszystkich powiązanych danych po dezaktywacji. WEB `lib/listings.ts:919`, `lib/api-client.ts:136–157`, `apps/web/next.config.ts:3–10`, API `clients/dto/import-clients.dto.ts:13`, `users/users.service.ts:382–389`.

## Kolejność napraw i warunki ponownej decyzji

1. **Przywrócić start i wiarygodną bramkę CI (PA-01, PA-18).** Zielony bootstrap pełnego modułu dla disabled i tpay, obie kompilacje i oba pełne zestawy jednostkowe. Zbudowany artefakt ma przejść również smoke inicjalizacji z właściwym schematem na stagingu.
2. **Przed udostępnieniem danych usunąć PA-02, PA-03 i PA-04.** Macierz dwóch agencji i kont sprzedawcy/agenta/admina, brak cudzych relacji w odpowiedziach; bezpieczne osadzanie treści na trzech rodzinach stron; odwołanie sesji i jednorazowy reset potwierdzone stanem bazy. Przejrzeć historyczne powiązania spotkań. Razem rozstrzygnąć PA-10 i wymagane ograniczenia adminów.
3. **Przygotować proces wdrożenia i odtworzenia (PA-05, PA-06, PA-09, PA-16).** Wykazać minimalny obraz bez plików środowiskowych, poprawione wersje runtime, osobny użytkownik procesu, ograniczone porty i tokeny CI, TLS i nagłówki na docelowych domenach. Przeprowadzić odtworzenie aktualnego schematu, DB i plików z jednego zgodnego punktu; udokumentować zmierzone RPO/RTO i osobę odpowiedzialną. Wyłączyć schema sync na produkcji.
4. **Dopiero wtedy rozważyć publiczną wersję darmową.** Odbiór moderacji i rzeczywistego rollbacku API (PA-11, PA-17), budżet bajtów i sprzątanie uploadów (PA-13), plan SQL katalogu (PA-14), limity CRM (PA-15). Uzyskać zgodną z polityką konfigurację weryfikacji kont, potwierdzić kontrolowane doręczenie, CSRF na docelowych subdomenach, limity proxy oraz alarm widoczny dyżurnemu. Sprawdzić darmowy cykl od zgłoszenia do publikacji i wycofania z katalogu. Przy niedostępnej sprzedaży UI i API muszą komunikować ten sam stan.
5. **Wydzielić odbiór jednorazowej sprzedaży (PA-07, PA-08).** Najpierw automatyczny test PostgreSQL obejmujący wycenę, wyścig checkoutów, promocję, unknown, brak waluty, duplikat i opóźnienie, zwrot i restart. Następnie osobno autoryzowany odbiór w Sandbox całej drogi nabywca → bramka → notyfikacja → publikacja → uzgodnienie, ze stanami po obu stronach i jednym grantem. Sprawdzić tenant, buyer, odbiorcę, kwotę i walutę w każdym kroku. Zatwierdzić regułę uprawnień po zwrocie i proces obsługi niepewnych wyników. Dopiero wynik tego odbioru uzasadnia decyzję o włączeniu.
6. **Sprzedaż cyklicznego PRO ma osobną decyzję.** Wymaga potwierdzonych capabilities konta, obsługi odnowień, błędów, rezygnacji i wygaśnięcia uprawnień oraz naprawy PA-12, jeśli generyczny billing uczestniczy w integracji. Zielone testy jednorazowego Tpay nie zamykają tych warunków.

**Obecna decyzja pozostaje NO-GO.** Najkrótszy mierzalny krok to usunięcie błędu DI i wykonanie smoke całej aplikacji. Warunkiem dopuszczenia pierwszych rzeczywistych danych są niezależnie zamknięte problemy izolacji, treści publicznej, sesji i odtwarzalności.
